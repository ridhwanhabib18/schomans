# CLAUDE.md — SchoMans

SchoMans is a school management system (attendance, grading, assignments, admissions,
announcements, approvals, AI features) built as a portfolio project.

## Source of truth
- Product requirements: `docs/en/PRD.md` (Indonesian copy: `docs/id/PRD.md`)
- System design: `docs/en/system-design.md`, diagrams in `docs/en/diagrams/`
- Decisions: `docs/en/adr/` (Indonesian copies in `docs/id/adr/`)
- Technical Q&A: `docs/en/technical-qa.md`
If code and docs disagree, stop and ask. Never invent requirements that are not in the PRD.

## How we work
- Work one phase at a time (PRD section 10). Do not touch features outside the current phase.
- Before coding a phase: list anything ambiguous in the PRD and ask.
- After a phase: run all tests, summarize changes, list deviations from the PRD,
  and store test evidence in `docs/assets/testing/phase-<n>/`.
- Do not add NuGet or npm packages without approval. Check the license first (see PRD section 6).

## Stack
.NET 10 LTS, ASP.NET Core Minimal API, EF Core 10, SQL Server 2022, Keycloak (OIDC + PKCE),
SignalR, Hangfire core, FluentValidation, QuestPDF, ClosedXML, AWSSDK.S3 (SeaweedFS locally,
Cloudflare R2 in demo), Serilog. Frontend: React 19 + TypeScript + Vite, TanStack Query (server
state), Zustand (client state), react-i18next, Tailwind + shadcn/ui, Recharts, orval.
Tests: xUnit, Testcontainers, Vitest, Playwright.

## Architecture rules
- Clean Architecture: Api -> Infrastructure -> Application -> Domain. Domain has no dependencies.
- Application is organized per use case: `Features/<Feature>/<UseCase>/` with Command or Query,
  Handler, Validator side by side.
- Business rules and status transitions live in entity methods (e.g. `request.Approve(approver)`).
- No generic repository; use `IAppDbContext`.
- External services (S3, Claude, PDF, email, SignalR) only behind interfaces in Application.
- Business errors are `Result<T>`, mapped to ProblemDetails by `ToHttpResult()`.
- NO mediator pattern: no MediatR, no Mediator library, no pipeline behaviors.
  Handlers are plain classes injected directly into endpoints (ADR-001).
- Two-layer authorization: role policy on every endpoint + ownership check in Application.

## Minimal API conventions (ADR-002)
- One file per feature in `Api/Endpoints/`, exposed as `app.Map<Feature>Endpoints()`.
  Nothing defined directly in `Program.cs`.
- One `MapGroup("/api/v1/<feature>")` per feature with tags and base policy.
- Endpoints point to named static methods, never long lambdas. No business logic in endpoints.
- Use `.WithValidation<T>()`, `.WithName("<OperationName>")`, `TypedResults`, `CancellationToken`.
- Explicit binding (`[FromBody]`, `[FromQuery]`, `[AsParameters]`) when in doubt.
- `IFormFile` endpoints use `.DisableAntiforgery()` (API uses JWT, not cookies).
- Uniform pagination: `page`, `pageSize` (max 100) -> `PagedResult<T>`.
- Every endpoint gets integration tests: success, validation failure, forbidden role (403).

## Frontend rules
- Feature folders: `web/src/features/<feature>/{api,components,pages,store.ts,i18n.ts}`.
- Components never call axios directly; use TanStack Query hooks in `features/*/api`.
- Zustand only for browser state, never a copy of API data; always use selectors.
- Features never import from each other; shared code goes to `shared/`.

## Language
- All code, comments, commits (Conventional Commits), branches, and PR titles in English.
- The app UI is English through i18n (`locales/en/*.json`); never hard-code UI text.
- Domain names follow the glossary in PRD section 6 (e.g. Wali kelas = HomeroomTeacher,
  Rapor = ReportCard, PPDB = Admission). Never mix languages in one identifier.
- Keep official acronyms: `Nisn`, `Nip`, `Nik`.
- Docs exist in English (primary) and Indonesian; update both in the same PR.

## Documentation
- Diagrams are Mermaid files in `docs/en/diagrams/`; ERD, API reference, and authorization
  matrix are generated by `tools/SchoMans.DocGen` and the `docs.yml` workflow.
- Screenshots only with fictional demo data; file names in English kebab-case.
